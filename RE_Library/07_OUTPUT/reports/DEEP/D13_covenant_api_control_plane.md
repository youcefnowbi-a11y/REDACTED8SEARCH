**Headline, stated up front so it is not buried:** Covenant's API layer is **1,084,841 B across 23,549 lines but only 183 operations** — it is an AutoRest-generated REST client façade with provably uniform structure. The authorization model is **not** in that file, and it is materially more rigorous than Sliver's: **17 of 17 API controllers carry a class-level `RequireJwtBearer` policy** across all 183 actions, and there is a real five-role Identity model. But there is **one unannotated 1,153-line SignalR hub — `CovenantHub`, mounted at `/covenanthub` with no `.RequireAuthorization()` — and it exposes exactly ONE live method, `CreateHttpListener`, which is a listener-creation entry point no gate reaches**, while all five of its sibling hubs carry `[Authorize]`. That is the D11 pattern repeating, and it is this report's primary finding.

**Correction carried in the header, not buried in §4.0:** an earlier draft of this report stated that `CovenantHub` had **~230 callable methods**. It has **one**. The other **222** public members are inside two block comments (`L35-161`, `L166-1151`). The error came from counting `public` tokens textually, which counts commented-out code. **A textual count is not a reachability count.** The measurement and its method are in §4.0; §8.4 revises what the finding means.

### 1.6 What this means for the security question

**The 1.08 MB file performs no authorization at all, and it is not supposed to.** It is a *client*. `CovenantAPI` is consumed by `CovenantService.cs` and `InternalListener.cs` to call Covenant's own HTTP API — the self-referential architecture D2 §1.2 documented. The `Credentials` property (`API/CovenantAPI.cs:34`) is a `ServiceClientCredentials` whose `ProcessHttpRequestAsync` is the only hook where a token is attached; there is no `Authorize` check anywhere in the file because there is nothing to check — it is the requester, not the responder. `[src]` + `[inference]`

**Consequence, and this is the load-bearing point for the whole report:** *the size of the client façade tells you nothing about the size of the authorization model.* D11's question — "does a framework's operator API carry its own authority, or does authority sit somewhere you'd never look?" — needs the **server-side controllers** to answer, not this file. Size was a red herring. `[inference]`

### 2.2 The JWT token itself

`[src]` — `Core/Utilities.cs:38-60`:

```csharp
public static string GenerateJwtToken(string UserName, string UserId, string[] Roles,
                                      string JwtKey, string JwtIssuer, string JwtAudience,
                                      string JwtExpireDays)
{
    List<Claim> claims = new List<Claim>
    {
        new Claim(JwtRegisteredClaimNames.Sub, UserName),
        new Claim(JwtRegisteredClaimNames.Jti, CreateSecureGuid().ToString()),
        new Claim(ClaimTypes.NameIdentifier, UserId)
    };
    foreach (string role in Roles) { claims.Add(new Claim(ClaimTypes.Role, role)); }
    SymmetricSecurityKey key = new SymmetricSecurityKey(Common.CovenantEncoding.GetBytes(JwtKey));
    SigningCredentials credentials = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);
    DateTime expireTime = DateTime.Now.AddDays(Convert.ToDouble(JwtExpireDays));
    JwtSecurityToken token = new JwtSecurityToken(
        JwtIssuer, JwtAudience, claims, expires: expireTime, signingCredentials: credentials);
    return new JwtSecurityTokenHandler().WriteToken(token);
}
```

**HS256, symmetric key, roles carried as `ClaimTypes.Role` claims.** Roles are baked into the token at issuance — this is what makes the `RequireAdministratorRole` policy work for JWT callers. `[src]`

### 2.4 `RequireHttpsMetadata = false`

`[src]` `Startup.cs:89`. The JWT bearer handler will accept tokens over plain HTTP. Combined with `[src]` `Startup.cs:93-96` validating issuer/audience/key and `ClockSkew = TimeSpan.Zero` (which is actually a *tightening* — no clock-drift grace is granted to expired tokens). `[src]`

The purpose is legitimate — Covenant's listener↔server channel is `https://localhost:port` and self-signed certificate validation is separately controlled — but the effect is that a bearer token is accepted from a cleartext transport. `[inference]`

### 2.5 Token retrieval from the query string — the SignalR bridge

`[src]` `Startup.cs:98-110`:

```csharp
options.Events = new JwtBearerEvents
{
    OnMessageReceived = context =>
    {
        var accessToken = context.Request.Query["access_token"];
        var path = context.HttpContext.Request.Path;
        if (!string.IsNullOrEmpty(accessToken) &&
            (context.HttpContext.WebSockets.IsWebSocketRequest ||
             context.Request.Headers["accept"] == "text/event-stream"))
        {
            context.Token = context.Request.Query["access_token"];
        }
        return System.Threading.Tasks.Task.CompletedTask;
    }
};
```

This is the **standard, documented ASP.NET Core pattern** for authenticating SignalR WebSocket connections, because browsers cannot set an `Authorization` header on a WebSocket handshake. It is gated on `IsWebSocketRequest` **or** `accept: text/event-stream`. `[src]`

**Two observations.** (a) The `access_token` is a full operator JWT travelling as a **URL query parameter**, which lands in server access logs and browser history — a known and accepted tradeoff of this pattern, but worth stating because Covenant logs to `Common.CovenantLogDirectory + "covenant.log"` with a NLog file target. `[src]` + `[inference]` (b) The `text/event-stream` alternative in the condition is broader than `WebSockets.IsWebSocketRequest` — any request claiming `accept: text/event-stream` gets its query `access_token` promoted to the bearer token. `[src]` This does **not** bypass authentication (the token must still validate), but it widens the surface on which a token may be presented. `[inference]`

### 3.3 The role model is therefore: a binary, enforced per-class, plus three decorative roles

**The enforced model is exactly one distinction: `Administrator` vs. not-`Administrator`.** `[src]` + `[inference]`

- All 18 API controllers require `RequireJwtBearer` — **authenticated, any role**. A plain `User` can call every one of them. That includes `GruntApiController` (`api/grunts`), `LauncherApiController` (`api/launchers`, 28,766 B — the largest controller), `ListenerApiController` (`api/listeners`), `GruntTaskingApiController` (`api` — tasking grunts), and `CredentialApiController` (`api/credentials`). `[src]`
- Exactly **three** actions restrict to `Administrator` — all in `CovenantUserApiController`: `:205` (`DeleteUser`), `:300`, `:326`. `[src]`
- The bootstrap check in `CreateUserVerify` is a **fourth** effective administrator check, but it is in the service layer, not expressed as a policy. `[src]`

**So: is the Administrator/User split enforced per-endpoint or only per-page? Answer: per-endpoint, but for only three endpoints plus one service-layer guard — and those three are all user-account administration.** `[src]`

**The consequence is the same shape as D11's `PermissionAll`, reached from the opposite direction.** On Sliver, every operator with `PermissionAll` can call every RPC and there is no separation between "view sessions" and "task implants." On Covenant, every **authenticated user of any role** can create listeners, generate launchers, task grunts, retrieve credentials, and read command output — the only thing a non-Administrator cannot do is manage *user accounts*. `[src]` + `[inference]`

**The `User` role is a full operator credential.** `[src]` — `CreateUserVerify:496` assigns every self-registered (or admin-created) account the `"User"` role, and nothing in the tree requires anything else. A `User` who is not an `Administrator` is a fully-capable C2 operator. `[inference]`

### 3.4 The `Listener` role is granted a 5.5-year non-expiring operator token

### 3.5 The `Administrators` plural — checked, and it is NOT a bug

`[src]` `Covenant.cs:251-259` contains a role check with a **plural** name:

```csharp

The method asks "is this *process* running elevated on this host," which is a startup diagnostic, not an operator authorization decision. The non-Windows branch checks for `root`. `[src]` + `[inference]` — **recorded here because it is exactly the kind of near-miss that reads as a finding and isn't.** The distinction between the two role namespaces is a real hazard for a reader auditing this file quickly.

- **No per-grunt, per-listener, per-profile, or per-task-family authorization exists.** `[src]` — no controller or hub method takes an ownership or scope parameter that is compared against the caller's identity. The `RequireJwtBearer` policy is the entire gate on 18 controllers. `[inference]`

- **No lockout / throttling configuration.** `[src]` — `PasswordSignInAsync(..., lockoutOnFailure: false)` at `CovenantService.cs:464`. `[inference]`

### 4.2 Why one method still matters

`CreateHttpListener(HttpListener listener)` is not a read-only accessor. It is the **listener-creation entry point**, and §3.4 established what that does when invoked: `[src]` `CovenantService.cs:3953-3970`

1. Creates a new ASP.NET Core Identity user (CSPRNG username, CSPRNG password).
2. Grants it the `Listener` role.
3. **Mints a 2000-day (≈5.5 year) JWT** for that user.
4. Stores the token on the listener record.
5. If `listener.Status == ListenerStatus.Active`, **starts the listener** — `StartInitialHttpListener(listener)` — which binds a network socket.

**Through a single unauthenticated SignalR invocation, a caller can therefore cause the server to provision a long-lived credentialed identity and start an HTTP listener.** The authority that should gate this is absent at the hub, and — per §2.8 — present on the REST equivalent: `ListenerApiController` (`api/listeners`) carries `RequireJwtBearer`. `[src]`

| Path | Gate |

### 5.4 The anonymous listener-facing endpoint — assessed

`[src]` `Controllers/ListenerControllers/HttpListenerController.cs` — **read in full, 122 lines.** It is `[AllowAnonymous]` at class level (`:21`) and again on the action (`:41`). It is the **third** anonymous surface in the tree, alongside login and first-user bootstrap.

**What an unauthenticated caller can do here:** `[src]`

- `Route()` (`:41`) accepts GET and POST. On **GET** it takes a GUID from the request (header or URL) and returns `await _internalListener.Read(guid)` — i.e. **whatever message the server has queued for that GUID.** On **POST** it extracts a message body via a profile-defined regex, calls `await _internalListener.Write(guid, ExtractedMessage)`, then **immediately reads back and returns the server's response** (`:56-58`). `[src]`
- GET → `_internalListener.Read(guid)` → `InternalRead` (`:352`) → the grunt/task handshake.
- POST → `_internalListener.Write(guid, body)` → the stage-0/1/2 handshake (`:408`, dispatching to `PostStage0` :582, `PostStage1` :684, `PostStage2` :726, `RegisterGrunt` :768).

**This is expected and architecturally correct:** the grunt is the caller and has no operator credential. Authentication of the calling grunt happens **inside the protocol** — HMAC over the ciphertext, RSA-OAEP key transport, and the stage guards D2 §3 documents (the `Status != Stage2 || !VerifyHMAC(...)` idiom, and the "always return NotFound" behaviour that avoids leaking state). `[src]`

**The real observation, and it is a real one:** the GUID is the *only* routing key, and `[src]` `GetGuid` (`:74-91`) accepts it from a **client-chosen header or URL path pattern**, with no binding to source address and no rate limiting on the endpoint. A caller who knows or guesses a valid grunt GUID can address the handshake for that grunt. The protocol crypto is what prevents success; the endpoint itself performs no admission control. `[inference]`

**Severity caveat, so this is not overstated:** the GUID space is 10 characters generated by `Guid.NewGuid().ToString().Replace("-","").Substring(0,10)` (`[src]` `InternalListener.cs:768+` region, D2 §3), i.e. hex — roughly 40 bits. Guessing is not practical, and every request beyond the correct stage is answered with `NotFound` indistinguishably from a nonexistent GUID. **The design relies on the crypto and the GUID, not on the controller.** `[inference]`

### 5.5 The RSA XML extension pair — worth recording for accuracy

`[src]` `InternalListener.cs:1027` `public static void FromXmlString(this RSA rsa, string xmlString)` and `:1059` `public static string ToXmlString(this RSA rsa, bool includePrivateParameters)`.

These are **hand-reimplemented** versions of `RSA.FromXmlString` / `RSA.ToXmlString`, which .NET Core removed (they existed on .NET Framework). D2 §3 recorded this. `[src]` The presence of hand-rolled ASN.1/`<RSAKeyValue>` parsing in the listener file — rather than in a crypto module — is an artifact of the .NET Framework → .NET Core port, and it is the code path that produces and consumes the grunt's session-key material. `[inference]`

**Not read line-by-line in this pass:** the two method bodies at `:1027-1090`. Stated as a gap, not covered.

## 6. Comparison against D11 §2

### 6.1 The two permission models, side by side

| | **Sliver** (D11 §2) | **Covenant** (this report) |
|---|---|---|
| Operator API size | `server/rpc/` — 83 files / 1,210 KB | `Controllers/ApiControllers/` — 17 files, 183 actions |
| Transport | gRPC | REST + SignalR |
| Authentication | Bearer token (SHA-256 stored) | JWT HS256 **and** Identity cookie |
| Roles | none — three booleans on the operator record | five Identity roles seeded, **one** enforced |
| Permission vocabulary | `PermissionAll`, `PermissionBuilder`, `PermissionCrackstation` | `Administrator` vs. not |
| `PermissionAll` equivalent | `PermissionAll` bypasses both remaining checks | **any authenticated user** bypasses role checks on 14 of 17 controllers |
| Where authority is enforced | **one 517-line middleware file**, adjacent to the API | per-controller class attributes (`RequireJwtBearer` ×17) + 3 method-level admin attributes |
| Per-endpoint authz in the API layer itself | **absent** | **present** |
| Local/unauthenticated transport | local socket — **no checks at all** | `/covenanthub` — **one unannotated method** |

`[src]` for Covenant, D11 §2/§4.4 for Sliver.

### 6.2 The three substantive convergences

**(1) Authority is displaced from the API surface — in both, but differently.** `[inference]` D11 found Sliver's `server/rpc/` (1.2 MB) carrying **zero** authorization logic, with all of it in `middleware.go` next door. Covenant's `CovenantAPI.cs` (1.08 MB) also carries **zero** — but for a different reason: it is a *generated client*, not the API implementation. The real Covenant API is `Controllers/`, and **there the authority is present and per-endpoint**. So the D11 finding generalizes as "the big file is never the authority file" but **not** as "these frameworks don't enforce auth in their API layer" — Covenant does. `[inference]`

**(2) The coarse role model converges, reached from opposite directions.** `[inference]` Sliver's `PermissionAll` means every operator with it can call every RPC, with no separation between viewing sessions and tasking implants. Covenant's `RequireJwtBearer` on 17 of 17 API controllers means every **authenticated user of any role** can call essentially everything, with no separation between a read-only analyst and a full operator. **Both arrive at "one privilege tier for all operational capability."** Sliver gets there by an explicit boolean; Covenant gets there by enforcing only one role and leaving every other role unread. `[inference]`

**(3) The second channel is the weak one, in both.** `[inference]` D11's finding was that Sliver's **local transport** had no authentication — a parallel path with no checks. Covenant's parallel path is **SignalR `CovenantHub`**: 1,153 lines, mounted at `/covenanthub`, and the only hub of six without `[Authorize]`. **In both frameworks, the alternate transport to the same capability is where enforcement lapses.** That is the transferable pattern from this report. `[inference]`

### 6.3 The two substantive divergences, stated fairly

**(1) Covenant has a real role model; Sliver does not.** `[src]` Covenant seeds five Identity roles and enforces `Administrator` on three user-management endpoints plus a service-layer bootstrap guard. Sliver has no role concept for operators at all — its booleans are service-account scoping, as D11 §2.1 concluded. **Covenant's model is more expressive and better implemented, and it is still effectively binary.** `[src]` + `[inference]`

**(2) Covenant authenticates its implant channel cryptographically; Sliver's local transport is unauthenticated.** `[src]` The `HttpListenerController` anonymous surface is not a hole — the grunt authenticates via HMAC/RSA/stage guards inside the protocol (D2 §3, `InternalListener.cs:513-820`). `[inference]`

## Summary

**The headline number and the headline finding are different things.**

`CovenantAPI.cs` at 1,084,841 B looks like the largest attack surface in the corpus. Measured, it is **183 copies of one AutoRest template** — 23,549 lines, one class, sixteen markers at exactly 183×, flat branching across every part of the file. It is a client the server uses to call itself, and it authorizes nothing because it requests rather than responds. `[src]`

The actual operator control plane is `Controllers/` — **183 actions across 17 API controllers, every one covered by a class-level `RequireJwtBearer` policy.** The REST surface is genuinely well-gated, and it is gated in the API layer itself, which is *not* what D11 found on Sliver. `[src]`

**The finding is the one place that pattern breaks.** `Hubs/CovenantHub.cs` is 1,153 lines, mounted at `/covenanthub`, and is **the only one of six hubs without `[Authorize]`** — while the other five, in the same directory, all have it. It exposes exactly **one** live method, `CreateHttpListener`, and the other **222** are inside block comments. That one method is not a read: it provisions an Identity user, mints a **2000-day** JWT, stores it on the listener, and can start a bound listener. A plain `User` can create listeners, generate launchers, task grunts, and read captured credentials. That is Sliver's `PermissionAll` outcome reached by a different route. `[src]` + `[inference]`

That left the open question of whether the *service* beneath the attribute supplied a second layer of checks. **It does not.** The service that implements all 183 operations contains **no authorization decision of its own** except the single first-user bootstrap guard.

**The general mechanism, and this is the transferable finding:**

> **The control existed in exactly one place — the controller attributes — and the alternate path was never that place. `CovenantHub.CreateHttpListener` reaches the same service method as `POST api/listeners`, but it enters below the attribute layer, and there is no second layer under it to catch the call.**

`[inference]` This generalizes the §4b pattern from "a control lapsed on an alternate path" to **why** it lapsed: the control was architecturally single-sited. This is the same shape as Sliver's transport interceptor (an in-process executor never passes through it) and Havoc's wrapper (a raw import need not use it). **In all three cases the alternate path bypasses nothing — it simply never enters the one place the check lives.** `[inference]`

### 8.3 The fifth artifact — an armed client with no consumer

**The probe's clean negative on the block-comment shape did not mean the pattern had run out.** Widening the detector to any class holding a `TokenCredentials` (i.e. anything that authenticates to Covenant's own API) surfaced a fifth artifact of a **different shape**, which is precisely why the comment-detector could not see it. `[src]`

`Core/CovenantAPIService.cs` — **3,951 B / 95 lines**, and it is **not commented out and not disabled**: `[src]`

```csharp
// Core/CovenantAPIService.cs:14-32
public class CovenantAPIService
{
    private readonly CovenantAPI _client;

    public CovenantAPIService(IConfiguration configuration)
    {
        X509Certificate2 covenantCert = new X509Certificate2(Common.CovenantPublicCertFile);
        HttpClientHandler clientHandler = new HttpClientHandler
        {
            ServerCertificateCustomValidationCallback = (sender, cert, chain, errors) =>
            {
                return cert.GetCertHashString() == covenantCert.GetCertHashString();   // <-- REAL pinning
            }
        };
        _client = new CovenantAPI(
            new Uri("https://localhost:" + configuration["CovenantPort"]),
            new TokenCredentials(configuration["ServiceUserToken"]),
            clientHandler
        );
    }

    public async Task CreateHttpListener(HttpListener listener)      // :33
    { await _client.CreateHttpListenerAsync(ToAPIListener(listener)); }

    public async Task CreateBridgeListener(BridgeListener listener)  // :38
    { await _client.CreateBridgeListenerAsync(ToAPIListener(listener)); }
}

`[src]` **Three properties, and they pull in opposite directions:**

1. **It is live in DI** — `[src]` `Startup.cs:194` `services.AddSingleton<CovenantAPIService, CovenantAPIService>();` — the live registration immediately above the three commented-out ones.
2. **It authenticates with the `ServiceUser` credential** — `[src]` `configuration["ServiceUserToken"]`. Per §3.2 and §3.4, `ServiceUser` is one of the **three roles granted but never required by any policy**. It is a full-scope operator token, not a scoped one.

```

`[src]` **Zero constructor injections, zero field references, zero call sites.** `CovenantService` does not take it as a dependency (verified: no `CovenantAPIService` occurrence in `CovenantService.cs`). Nothing in the tree calls `CreateHttpListener` or `CreateBridgeListener` on it.

**Assessment — and the discipline matters here:**

**This is dead-but-retained, not a live path.** `[inference]` It is resolved by DI at startup and therefore **instantiated**, but no code path invokes its two methods. That is the same status as `CovenantHubService`: capability present, reachability absent.

**It is the reverse of §4's shape, and that is why it is worth recording.** `CovenantHub.CreateHttpListener` is *reachable but ungated*. `CovenantAPIService.CreateHttpListener` is *gated but unreachable*. Both are the same underlying confusion — a listener-creation entry point living outside the controller layer. Covenant has **four** paths to `CreateHttpListener`:

| Path | Entry | Gate | Reachable |
|---|---|---|---|
| 1 | `POST api/listeners/http` → `ListenerApiController:156` | `RequireJwtBearer` (`:17`) | **yes** |
| 2 | SignalR `/covenanthub` → `CovenantHub:162` | **none** | **yes** |
| 3 | `InternalListener` → `_client.CreateHttpListenerAsync` (`InternalListener.cs:112-116`) | JWT via `TokenCredentials` | **yes**, when a listener is created |
| 4 | `CovenantAPIService:33` → `_client.CreateHttpListenerAsync` | `RequireJwtBearer` at the target | **no** — no consumer |

`[src]` for the entry points and gates; `[inference]` on reachability. **Path 2 is the only one of the four with no gate.**

**Why the cert-pinning detail matters, if it were ever re-registered.** `[inference]` Unlike `CovenantHubService.cs:30-33`, which stubs its callback to **`return true` unconditionally**, `CovenantAPIService` implements **real certificate pinning** (`cert.GetCertHashString() == covenantCert.GetCertHashString()`) — and it is the same technique `InternalListener` uses. So this artifact is better-built than the disabled one next to it. The risk it carries is not a stub; it is that it holds a **`ServiceUser` token with no role requirement** and two unrestricted listener-creation methods. If a future change injects it into a controller or a startup path, it would present a fully-privileged client with no scope limit and no consumer-side check — and nothing in its own code would object. **Stated as `[inference]`: capability present, reachability absent, and the only thing preventing reachability is that no one has written a call site.** `[inference]`

**The reading this supports — a revision to §4.4.** `[inference]` §4.4 concluded that the block-commented hub "was being developed as a permission-blind mirror, and the author discovered it and disabled it." §8.1-§8.3 support a sharper version: the author had built a **two-process topology** in which the Blazor/Razor front end would talk to a SignalR service proxy (`CovenantHubService`, `CovenantBlazorService`, `SignalRCovenantService`) rather than directly to `CovenantService`. `[src]` `CovenantHubService` is literally `IRemoteCovenantService` — the *remote* implementation of the operator service, the local one being `CovenantService`. **The hub was the server half of that split.** When the split was abandoned, both halves were dismantled asymmetrically: the hub's methods were block-commented but the class was left mapped at `/covenanthub` with one method left live; the proxy was disabled at DI but left in the tree. **The result is artifact 1.** `[inference]`

**The correction to my own §4 framings is therefore substantive, not cosmetic:** `CovenantHub` is not "an unprotected hub that nobody noticed." It is **the surviving half of a deliberately abandoned architecture, and the one method left live in it is a listener-creation entry point that the abandonment never gated.** The live/comment boundary at `L161/162` is the exact line where the author stopped commenting. `[inference]`
